# Error Handling

app 层负责结合业务场景决定是否处理错误、是否需要用户感知以及使用什么方式展示。错误来源、异常类型和展示方式不是一一对应关系；不要看到 `error` 或 `catch` 就默认把错误渲染到界面。

## 分层职责

- API client 层负责 baseURL、鉴权、响应解包、后端错误协议适配和错误文案解析。
- `$req` 层负责 loading、error、data、retry、pagination、infinite、notify 等请求状态。
- 页面和 feature 层负责解释权限失败、提交失败、流程中断和字段错误，并决定是否使用 `$toast`、路由级错误页或其他业务反馈。
- 组件层只消费已经解释的状态并渲染，不重新猜测 API 协议。

## 判断顺序

处理错误时依次判断：

1. 当前组件、请求能力或业务模块是否已经内置符合场景的错误处理。
2. 当前层是否需要处理该错误。
3. 错误是否需要用户感知。
4. 错误是否导致某个内容块无法继续展示。
5. 是否存在符合业务语义的降级结果。
6. 当前层处理后是否还需要继续抛出。

## 默认已处理：AI 通常无需关心

以下行为已由当前 app 基础设施或组件契约处理。除非任务正在修改这些基础设施、调用方显式关闭或绕过默认能力，或已有证据表明默认行为失效，AI 在实现和代码审查时不重复要求调用点补写同类错误处理。

| 场景                                                | 默认处理                                                                    | AI 通常不需再做                                       |
| --------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| 使用 Schema Form、SchemaField 和 Zod 的前端表单校验 | 字段附近展示校验错误，无效提交不进入成功提交流程                            | 不另写一套校验文案渲染，不为同一字段错误弹 `$toast`   |
| 通过当前 `$api` / `$req` 默认 client 发起的接口请求 | `createApi.notify` 默认对请求失败调用 `getErrorMessage` 并分发错误 `$toast` | 不在每个调用点为相同失败补 `catch` 和重复 `$toast`    |
| 取消或中止请求                                      | `createApi.notify` 默认不展示失败通知                                       | 不把取消当成普通失败弹 `$toast`                       |
| 文件路由下的未匹配子路由                            | Vite 路由生成阶段已通过 `injectHttp404Routes()` 注入路由级 404 兜底         | 不在业务页重复添加 catch-all 路由或手动判断未匹配路由 |

默认处理只代表对应的校验展示、通知或路由兜底已完成，不代表错误被吞掉，也不代表业务影响已恢复。`$req.error` 仍需要根据场景决定是否替换内容块；`ErrorState` 只提供通用展示能力，不会自动判断或处理业务错误。

AI 只在以下情况重新审查上述默认处理：

- 调用方使用 `notify: false` 或覆盖了默认通知策略。
- 调用方绕过 Schema Form、`$api` / `$req` 或文件路由配置。
- 自动重试、后台请求或其他特殊流程需要改变通知时机。
- 产品要求不同的错误文案、恢复操作、业务降级或内容块错误态。
- 测试、日志或实际运行结果证明默认处理没有生效。

对其他组件，已经提供符合场景的错误状态、校验或恢复能力时，调用方直接消费其公开契约。内置处理不符合当前场景时，显式关闭或覆盖，再由业务层接管。不凭组件名称猜测能力，以公开文档、props、events 和 slots 为准。后端字段错误是否能自动映射取决于实际接入；没有明确契约时，仍由业务层映射到对应表单字段。

## 当前层无需处理

当前层不关心错误结果，也不负责恢复、通知、记录或降级时，不添加 `catch`，让异常继续交给调用方、框架错误处理器或运行时。

- 当前流程需要等待结果时直接 `await executeTask()`。
- 不依赖执行顺序和结果时可以使用 `void executeTask()`。
- 不为了形式上“处理过”而添加空 `catch`、`catch(() => undefined)` 或等价逻辑。

## 仅需开发者感知

错误不影响用户当前任务，但需要诊断时，可以输出到控制台或上报监控。控制台和监控属于诊断渠道，不等同于用户通知。

## 需要用户感知

用户需要知道操作结果时，可以使用 `$toast`。是否同时需要替换某个内容块，继续根据错误的实际影响范围判断。

- 保存、删除、复制、提交等明确操作的结果适合使用 `$toast`。
- 需要用户持续关注的重要通知使用常驻 `$toast`，并提供必要的操作或关闭入口。
- 自动请求、轮询和后台刷新失败默认不通知；只有错误会影响用户判断或需要用户介入时才通知。

## 阻断内容块

错误导致某个内容块无法继续展示时，使用 `ErrorState` 替换受影响的内容块。路由业务区、面板、卡片、表格等都可以根据实际影响范围使用，不因错误来自 HTTP 请求就默认扩大替换范围。

返回、返回首页、重试、刷新、重新登录或申请权限等恢复操作由 `ErrorState` 的 `actions` slot 提供。明确的 HTTP 路由状态，例如 404，使用 `@ngt/ui/http` 中的对应路由级组件。

## 业务降级

错误发生后是否返回空数组、空对象、默认值、缓存数据或其他降级结果，由具体业务语义决定，不做统一禁止。

降级结果应具有明确业务含义，调用方能够正确解释该结果；不仅为了消除类型错误、避免异常传播或让页面强行渲染而机械返回默认值。是否同时记录错误或通知用户，同样由当前业务决定。

## 错误文案

- 能够识别具体原因并提供稳定用户解释的可预期错误，使用 app i18n 文案。
- 无法提前识别或分类的不可预期错误，允许展示原始错误文案。
- 原始错误没有可用文案时，使用通用 i18n 错误文案兜底。
- 接口错误文案由对应 `createApi` 实例的 `getErrorMessage` 统一解析。首次对接后端时根据实际错误协议完成适配，不预设固定错误字段。
- 页面、组件和 feature 不重复解析后端原始错误响应。
- `getErrorMessage` 只负责生成错误文案，不决定使用 `$toast`、`ErrorState`、HTTP 路由状态、控制台或其他处理方式。

## catch 约束

`catch` 应有明确目的，例如转换错误、恢复或回滚状态、提供业务降级、通知用户、切换错误页、输出诊断信息或补充上下文后继续抛出。当前层没有这些职责时，不捕获错误。

## 公共包边界

- 不要求 `@ngt/ui` 理解业务错误或后端错误协议。
- 不要求 `@ngt/ui` 写具体业务文案或业务流程处理。
- app 可以覆盖 `@ngt/ui` 默认文案，也可以把 `@ngt/ui` 标准错误状态解释成业务反馈。

## Checks

- 是否把已有默认处理误报为调用点缺失，或在调用点重复实现。
- 是否只在默认处理被关闭、绕过、覆盖或已有失效证据时重新审查。
- 当前层是否真的需要 `catch`。
- 用户是否需要感知该错误。
- `$toast` 是否表达用户需要感知的结果，并且不与当前界面状态冲突。
- `ErrorState` 的替换范围是否与错误的实际影响范围一致。
- 明确的 HTTP 路由状态是否使用 `http` 模块中的对应组件。
- 可预期错误是否使用 i18n，不可预期错误是否正确保留原始文案。
- 页面是否重复解析已在 API 接入层适配的错误协议。
- 默认值或空结果是否具有明确的业务降级语义。
- 当前层处理后是否还需要继续抛出。

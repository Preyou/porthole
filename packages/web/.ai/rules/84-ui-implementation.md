# UI Implementation

新增业务界面时，默认使用项目系统样式和主题 token。

## 默认界面

- 新增页面、feature 或业务组件时，总是使用系统默认样式。
- 写界面前，先评估本次可能用到的组件类型、交互形态和状态。
- 评估后必须按 `.ai/public/shared-capability-usage.md` 发现和选择相邻实现、`@ngt/ui` 的相关组件、组合组件或变体。
- 如果 `@ngt/ui` 的组件可以直接使用，或经过组合后能满足需求，必须优先使用这些组件。
- 优先复用相邻页面、app 共享组件、`@ngt/ui`。
- 布局语义标签可以正常使用，例如 `main`、`section`、`div`、`span`。
- 只有文字自身承担独立排版层级时，才使用 `@ngt/ui/text` 的 `Text`，例如页面标题、独立正文、说明和辅助信息。
- 不要仅因为模板节点中包含文字就使用 `Text`。移除所属组件后，文字仍需要明确的 `variant` 时才使用 `Text`。
- Button、Badge、菜单项、下拉选项、Tabs Trigger、导航项、Label 以及其他已管理字号、字重或行高的组件应直接接收文字，禁止为其普通文字内容再嵌套 `Text`。
- `Text` 的默认 `body` 会重置核心排版属性，不受父级字号、字重等影响；所以它不应作为通用的文字包装层。
- 业务页面不用字号、字重、行高和字距工具类重新实现 `Text` 已有的独立文字层级。
- 只有要手写可由 `@ngt/ui` 表达的控件或交互组件时，才需要先说明当前 `@ngt/ui` 组件不满足的具体原因，并获得开发者同意。
- 不为单个页面写独立配色、独立视觉风格或脱离主题系统的样式。
- 样式问题默认交由主题系统、组件变体和 token 解决。
- 如果确实需要新增视觉语义，先判断它是否应该成为主题 token、组件 variant 或业务组件状态。

## 尺寸控制

- 设置尺寸前，分别判断宽度和高度的决定方式：由外部布局分配空间，还是由内部内容撑开。两种方式可以组合，并随使用场景或方向变化；不按元素名称或“布局类 / 交互类”固定分类。
- 由外部布局分配空间时，优先通过父子布局关系、百分比尺寸或 Flex/Grid 表达占用空间和伸缩方式。
- 由内部内容撑开时，需要限制整体尺寸，优先约束内部承担自由伸缩的区域，保留其他区域的自然尺寸；只有整体布局或明确尺寸契约要求时，才直接约束外层容器。
- 外部分配空间与内部最小空间需求可以同时存在。内部元素确有不可继续收缩的尺寸需求时，优先通过其自身尺寸、内容、`padding`、`gap` 和伸缩关系自然形成整体的最小空间，不在外层硬编码或手动累加内部尺寸来重复计算 `min-width` / `min-height`。
- 例如“标题栏 + 内容区 + 操作栏”面板，优先控制可伸缩内容区的尺寸，标题栏和操作栏按自身需求占位；不要为表达面板的最小空间，手动计算三者高度及间距之和。
- 区分必须保留的最小空间和允许收缩的内容区域；按当前布局契约安排换行、截断或滚动，需要时允许对应区域收缩，不机械地保留所有内容的自然最小尺寸，也不逐层清除全部最小尺寸约束。
- 明确的整体尺寸或最小交互尺寸契约仍可直接表达，优先复用组件 `size`、variant 或设计 token；不要为避免数值约束而增加无意义的内部占位元素。

## 主视图区与空间分配

本节适用于页面、布局、Header、卡片、弹窗等各层级组件。先判断视觉任务，再确定空间分配，最后选择具体布局实现。

- **按视觉任务识别**：主视图区是组件中承担主要内容展示或交互任务的区域，不能仅凭面积、位置、DOM 层级或组件类型判定。一个组件可以有零个、一个或多个主视图区。
- **尺寸只是线索**：宽或高至少有一个方向跟随父容器的组件，通常至少有一个主视图区；具有固定宽或高的组件通常也有；宽高完全由内容决定的组件通常没有。这些不是绝对条件，最终仍以组件承担的视觉任务判断。
- **明确每个区域的职责**：实现前确定主视图区的数量、负责的伸展方向、空间分配关系和边界。多个主视图区按任务分配比例及必要的最小/最大尺寸，不默认把最大或居中的区域当作唯一主视图区。
- **按负责方向填充**：主视图区默认承接并填充该方向的剩余可用空间，可以只水平伸展、只垂直伸展或同时伸展；其他区域按各自任务占位，不机械地让所有区域伸展。
- **插槽也能承载主视图区**：主视图区可以由内部结构、子组件或插槽承载。宿主组件定义插槽所在区域的空间、伸展与溢出契约，传入内容遵守该契约。例如 Header 左侧标题、右侧状态按任务占位，中间插槽承载顶部菜单并承担主要导航任务时，该插槽区域就是水平方向的主视图区，填充剩余宽度；不能把它只理解成留白。
- **内部布局继续按任务判断**：外层主视图区填充剩余空间，不代表其中每张卡片、每个字段或所有后代都需要伸展。子组件仍可自然撑开、继续填充或划分自己的多个主视图区；不逐层机械添加 `flex-1`。
- **兑现尺寸和溢出契约**：使用 Flex/Grid 表达空间关系，保证父子尺寸约束能够传递；需要时用 `min-h-0`、`min-w-0` 允许收缩。根据任务明确滚动、截断或换行的归属，避免各层自行增加滚动容器；主视图区不自动等于滚动区，也不一律要求占满视口。

- **自然尺寸与等高**：完成主视图区识别后，按内容撑开的普通容器、卡片内容、列表项、设置项和选项控件继续由内容、`padding` 和 `gap` 决定尺寸，不用数值型 `min-h-*` 制造视觉空间。同列或同组需要等高时，优先使用 Grid/Flex 拉伸或父级布局，不为每个子项设置数值型最小高度。
- **明确的最小高度例外**：数值型 `min-height` 只用于有明确产品尺寸契约的场景，例如最小点击区域或固定初始编辑空间；优先通过组件 `size`、variant 或 token 表达，页面层直接使用 `min-h-24`、`min-h-40` 等工具类必须说明理由。用于收缩的 `min-h-0`，以及用于明确视口契约的 `min-h-svh` / `min-h-screen`，不属于制造视觉留白。

## 截图还原

- 带截图、Figma、MasterGo 或设计稿要求还原时，不要默认把它当成单页静态稿直接实现；先做 Scope Check。
- 截图还原不是截图转代码。先判断它在产品路由、业务结构和组件体系中的位置，再做视觉实现。
- 带截图要求还原时，先识别截图中的布局结构、信息层级、交互状态、基础组件和组件变体。
- 尽可能把截图中的结构映射到项目已有组件和变体。
- 无法映射到现有组件时，可以新增对应业务组件。
- 截图、Figma、MasterGo 或同批设计稿还原后，必须做一次轻量重复结构检查；不要只按画面顺序堆模板。
- 截图只作为布局、结构、组件选择和状态识别依据。
- 不参考截图中的配色、阴影、圆角、字体风格、品牌色或整体视觉风格。
- 截图还原后的界面仍必须使用系统默认主题。
- 不为了贴近截图而写硬编码色值、私有主题、局部设计语言或绕开 shadcn token 的样式。

Scope Check 分级：

- Full Restore：新 app、新模块、多页面、多张截图或完整设计稿节点。编码前必须先产出路由结构、组件结构、组件来源和自封装组件设计。
- Local Page Restore：已有模块内新增或改造一个页面、一个设置界面或一个业务界面。不重做全局架构，但必须先确认父路由、同级 route pages、当前 feature/components 或相邻组件目录。
- Small Patch：已有页面内的小范围样式、文案、字段、按钮或局部交互调整。不需要输出完整路由计划，但必须检查当前文件和直接相邻组件是否已有可复用结构或基础组件。

Full Restore 编码前必须确认：

1. 路由结构：哪些业务位置进入 URL，哪些是父布局，哪些只是局部状态。
2. 组件结构：重复或相似结构列表，哪些抽组件，组件放哪里。
3. 组件来源：按 `.ai/public/shared-capability-usage.md` 查找当前业务库、`@ngt/ui` 与自封装边界。
4. 自封装组件设计：props、slots、events、父子职责边界。

Local Page Restore 最低检查范围：

```txt
src/views/<route-page>.vue
src/features/<page-or-feature>/**
src/components/<related-group>/**
```

需要检查父路由、同级路由或子路由时，只读取 `src/views` 中实际对应 URL 或父布局的路由页；不要把页面私有组件目录当成 `views` 的相邻结构。

如果目标模块不明确，先根据截图和现有路由推断最可能归属；推断风险较高时再询问开发者。

轻量重复结构检查只做一次，范围限定为：

1. 本次新增或修改的路由页与对应 feature/component 中的组件。
2. 同一 feature、同一路由分组下的相邻页面。
3. 本次从同一个设计稿还原出来的一组页面或状态。

命中以下任一情况时，应优先抽组件并用数据驱动差异：

- 相同布局骨架出现 2 次以上，例如 icon + title + description + trailing action。
- 相同交互语义出现 2 次以上，例如设置项、文件项、任务行、会话行、导航项、信息列表项。
- 相同状态表达出现 2 次以上，例如 selected、loading、done、disabled。
- 只是文案、图标、按钮文字、状态不同，布局和交互一致。

检查预算：

- 不做全仓库相似结构扫描。
- 最多列出 3 类明显重复结构。
- 只处理当前改动范围和相邻上下文内的明显重复项。
- 不因为页面内重复结构检查读取 `@ngt/ui` 全量资料；只有判断要上提公共包时，才按公共能力选择流程继续读取资料。

## 组件边界

- 写具体组件前，必须按 `.ai/public/shared-capability-usage.md` 查找合适组件；都不满足时，才自行封装。
- 自行封装可复用组件时，先明确自身布局、可替换内容、props、slots、events、内部状态和父组件控制边界。
- 自行封装具体业务组件时，先明确业务数据如何传入、由哪些基础组件组合而成、业务行为归属哪里。
- 组件缺少简单变体时，考虑补到 `@ngt/ui`。
- 领域中立的复杂组合能力，考虑补到 `@ngt/ui`。
- 具体业务结构或流程，留在 app 业务组件。
- 业务组件变大时，先识别相对固定、功能单一的结构，并拆分为有清晰层级的子组件。
- `src/features` 中的组件文件结构应跟随组件组合层级，父组件文件与同名目录并列，子组件放入父组件同名目录。`src/components` 确需多级拆分时也遵循该规则；`src/views` 不适用。
- 重复结构先按复用范围放置：当前页面对应的 feature 目录、feature/app 共享目录、`src/components`、`@ngt/ui`，不要跳级。
- 新增业务组件也应消费主题 token，不直接固化截图视觉。

## Checks

- 是否按方向和场景判断尺寸来源，优先约束内部伸缩区，并让必要的内部尺寸需求自然形成最小空间，避免外层重复计算。
- 是否先做 Scope Check，并按 Full Restore、Local Page Restore 或 Small Patch 选择了合适强度的规划。
- 是否先确认当前功能在路由、feature、组件体系中的归属，而不是只把截图插入页面。
- 是否在写界面前评估了可能用到的组件。
- 是否按 `shared-capability-usage.md` 的顺序查看并优先使用了相邻实现、`@ngt/ui` 的相关能力。
- 是否通过 `@ngt/ui` public 索引和 README 确认了候选能力，而不是凭记忆猜测。
- 是否只从 package exports 导入公共能力。
- 原生标签实现前是否说明了 `@ngt/ui` 不满足的原因并获得开发者同意。
- 是否优先复用了已有组件和变体。
- 是否仅从截图提取结构和组件语义，而不是复制视觉风格。
- 是否对当前改动、相邻页面和同批设计稿状态做了一次轻量重复结构检查。
- 是否把明显重复的业务结构抽为合适层级的组件，而不是复制同类 DOM。
- 是否避免硬编码颜色和脱离主题系统的样式。
- 是否按视觉任务明确了主视图区的数量、伸展方向和边界，包括由子组件或插槽承载的区域。
- 是否兑现剩余空间分配与父子尺寸契约，并按任务安排内部自然尺寸和溢出处理，避免机械伸展或重复滚动。
- 保留的数值型 `min-height` 是否存在明确尺寸契约，并已优先考虑组件 API、token 或父级布局。
- 无法映射的部分是否放在合适层级。
- 复杂组件是否拆分出稳定、单一职责的子组件，并使用匹配的文件层级。

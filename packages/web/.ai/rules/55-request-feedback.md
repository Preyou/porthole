# Request Feedback

业务层请求应保持协议、分页、提示和失败语义一致。

## 加载态

- 加载态表达用户当前操作或内容区域正在等待，不与每个请求机械对应。默认保持界面稳定和可交互，只在最小受影响范围内提供反馈。
- Vue 组件内的请求优先使用 `$req`（`@ngt/ui` `createRequest` 创建的 `useRequest`），并直接消费其 `loading`、`pendingCount`、`status`、`data` 和 `error`。不另行使用 `ref(false)` 与 `try/finally` 重复维护请求 loading。
- `$req.loading` 表示当前请求实例中 `pendingCount > 0`，不表示浏览器一定产生新的网络请求。命中缓存、共享在途请求和限频等待都可能使请求流程、`loading` 和实际网络传输不同步。
- Starter 的 `$req` 默认以 `auto` 模式联动全局 `$loadingBar`，只跟踪用户显式发起的请求操作；初始化、watch、轮询和关联后台刷新保持静默。单个请求需要不同策略时使用 `loadingBar` 配置覆盖。
- 直接使用 `$api`（`@ngt/ui` `createApi`）只返回 Promise，不提供 Vue 响应式请求状态。需要按请求状态渲染界面时优先使用 `$req`；action、store 或流程函数直接使用 `$api` 时，由最近的交互边界决定是否需要可见加载态。
- 缓存命中或快速请求可能使可见加载态一闪而过。对强视觉反馈必要时使用统一的延迟展示策略；请求在阈值前结算则不展示，也不为满足最短动画时长而延迟已可用内容。
- 首次加载且没有可展示内容时，在对应内容区域使用与最终结构接近的 Skeleton。已有数据的 `refresh`、polling、watch 联动或后台同步优先保留原内容，必要时只展示轻量的局部刷新标识。
- 首次加载失败应进入明确的错误态，可恢复时提供重试入口。空状态只表示请求成功但没有数据，不表示请求还在加载或已经失败。
- 提交、保存等 mutation 优先在触发按钮内展示 Spinner，需要防止重复提交时只禁用相关控件。结果可预测、失败可回滚且冲突风险可控时，优先使用 `run(params, optimistic)` 或 `forceRun(params, optimistic)` 的乐观更新。
- `refreshTargets` 触发的目标刷新由目标请求实例自己的 loading/error 表达，不将源 mutation 与后台刷新合并成页面级 loading。
- 同一 `$req` 实例的 `loading` 会聚合其所有活动调用。多个表格行或局部操作可以独立执行时，应保留局部 pending 身份或拆分交互边界，不因任意一项请求禁用整个容器。
- 可计算进度的上传、下载或长任务优先使用 `uploadProgress` / `downloadProgress` 或业务进度，不只展示无限旋转的 loading。
- 只有处理期间必须阻止交互时才使用遮罩，并把遮罩限制在受影响容器内。页面无法展示任何有意义内容且必须阻止全部交互时，才使用页面级 loading。
- 加载反馈应提供 `aria-busy`、`role="status"` 或可访问名称，并避免导致焦点丢失、布局跳动或无关内容不可操作。完整场景选择和 `@ngt/ui` Request 状态语义见 `.ai/public/request-usage.md` 的“加载态表达”。

## 分页协议

- 业务层分页参数统一使用 `page`、`pageSize`。
- 分页结果统一映射为 `list`、`total`，并保留当前 `page`、`pageSize` 状态。
- 对接第三方接口或历史后端时，可以在 API 接入边界做一次字段适配。
- 不在页面、组件或 feature 内混用 `page_size`、`size`、`limit`、`offset` 等别名作为主路径。
- 使用 `$req` 分页能力时，`toParams` 应输出统一分页参数，`fromResponse` 应映射统一分页结果。

## 提示边界

- 全局提示只用于需要用户立即感知的重要结果。
- 同一个请求结果可以同时驱动通知和界面错误状态；各反馈的结果、文案和恢复操作不得互相冲突。
- 当前默认 `$api` / `$req` client 已开启请求失败自动提示。除非调用方关闭、覆盖或绕过该能力，AI 不要求在每个调用点补写相同失败的 `catch` 和 `$toast`；默认已处理清单与审查例外见 `56-error-handling.md`。
- 页面仍可以根据请求错误渲染与通知一致的界面状态。
- 页面层需要完全接管 toast 文案或触发时机时，应在请求配置中关闭对应自动提示。
- 表单校验错误、字段级后端错误，应展示在表单项附近，不使用全局 `$toast`。
- 自动加载、watch 联动、轮询、后台刷新默认不做成功提示。
- 局部状态变化、轻量刷新完成等用户可通过界面感知的结果，默认不提示。

## 失败语义

- 当前层不需要处理业务请求异常时，不添加 `catch`，让异常继续传播。
- 只需开发者诊断且不影响用户当前任务的失败，可以输出控制台或上报监控。
- 是否返回默认值、空结果、缓存数据或其他降级结果，根据具体业务语义决定。
- 不可恢复的请求错误应进入明确失败态或继续抛出。
- 可以提示用户，但提示不能替代失败状态。

## Checks

- 是否直接消费 `$req` 的状态，而不是重复维护请求 loading。
- 是否区分首次加载、已有数据刷新、mutation 和后台同步。
- 加载反馈是否只影响最小必要范围，遮罩和页面级 loading 是否真有阻断必要。
- 分页参数和返回结果是否统一。
- 第三方协议差异是否只在边界适配。
- 是否出现含义重复的 toast、相互冲突的提示或过度成功提示。
- 表单错误是否错误地使用全局提示。
- 失败路径的错误状态或降级结果是否符合具体业务语义。

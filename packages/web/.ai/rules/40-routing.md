# Routing

app 使用 `unplugin-vue-router` 基于 `src/views` 生成路由。

## 什么应该成为路由页

路由页应表达用户可直接访问的业务位置。判断核心是：这个界面状态是否值得被 URL 表达。

适合放进 `src/views`：

- 用户需要直接访问、刷新、分享或收藏的页面。
- URL 本身表达业务对象或业务位置的页面，例如列表、详情、设置、报表。
- 有独立导航入口的页面。
- 需要参与权限、菜单、面包屑、页面标题或访问埋点的页面。
- 浏览器前进/后退有明确意义的页面。
- 刷新后需要恢复同一业务上下文的页面。

不适合做成路由页：

- 页面内部局部组件，例如 toolbar、筛选面板、表单分组、信息卡片。
- 普通弹窗、抽屉、popover。
- 纯 UI 状态，例如 hover、focus、collapse、下拉菜单打开状态。
- 没有独立访问价值的一次性业务组件。
- 不需要刷新恢复、分享或后退前进的流程中间步骤。

边界情况：

- 弹窗或抽屉如果需要分享 URL、刷新恢复或浏览器后退关闭，可以考虑路由化。
- tab 如果表达重要业务视图并需要 URL 恢复，可以考虑路由化；普通局部 tab 留在组件状态。
- 代码复杂度不是路由化理由，URL 语义才是。

## URL 状态

URL 不只是定位页面，也可以承担轻量临时状态存储。

适合放进 URL：

- 查询关键词。
- 列表筛选条件。
- 分页页码。
- 排序字段。
- 重要业务 tab。
- 当前选中的业务对象 ID。
- 报表时间范围。
- 需要刷新恢复的流程步骤。
- 非敏感、轻量、刷新后不应丢失的表单数据。

不适合放进 URL：

- 密码、token、验证码、手机号、身份证号、邮箱、详细地址、隐私备注等敏感信息。
- 大段文本、富文本、文件内容。
- 大型对象或复杂嵌套 JSON。
- 频繁变化的 UI 状态。
- 纯视觉状态。
- 不稳定的内部实现字段。

## URL 表单数据

- URL 只存放经过筛选和稳定编码的非敏感轻量状态。
- 表单数据放入 URL 前，必须先判断字段是否适合暴露。
- 编码不是脱敏或加密，敏感数据禁止进入 URL。
- 编码使用 URL/query 标准编码即可，不使用 base64 包装。
- 复杂筛选条件可以统一编码成单个 query 参数，例如 `q`、`filter`、`state`。
- 不要直接把完整表单对象 `JSON.stringify` 后塞进 URL，除非明确确认字段都是非敏感且体积可控。
- 如果需要恢复敏感或复杂草稿，应使用 sessionStorage、localStorage 或 draft API，而不是 URL。
- query key 应稳定、可读、可兼容，不直接暴露不稳定的内部字段名。

## 页面

- 新页面放在 `src/views`；只有真实路由页面可以进入该目录。
- `src/views` 中的每个文件都必须直接对应一个 URL 页面或父布局路由。禁止放非路由组件、composable、状态、工具和测试文件。
- 文件路径决定路由路径，放入其中的 `.vue` 文件会被文件路由插件处理。
- `definePage()` 是可选的路由配置宏，不是路由页标记。普通页面应直接使用文件路由默认值，不推荐为了声明“这是页面”或重复默认配置而调用它。
- 是否使用 `definePage()` 只取决于页面是否存在明确且必要的自定义路由配置需求。重定向、页面级路由守卫，以及供导航、权限、菜单、面包屑等能力消费的 route meta 都是常见示例，但不是允许场景的穷举；使用时只声明当前需要的字段。
- 兜底 404 路由由 Vue Router 文件式路由插件在生成阶段自动注入，不在 `src/views` 手写 catch-all 页面。
- 404 页面组件由 `@ngt/ui/http` 提供，注入逻辑由 `@ngt/ui/utils` 的 `injectHttp404Routes()` 承载。helper 在源码联调与预构建安装中会自动选择对应的组件文件。

路由页的职责：

- 路由页可以包含简单页面布局和编排内容，例如页面标题区、顶部工具栏位置、筛选区容器、内容区骨架、`RouterView` 容器、URL query/params 到子组件 props 的桥接。
- 路由页确有需要时，可以通过 `definePage()` 声明与当前页面访问语义绑定的路由守卫、路由鉴权、权限 meta、进入条件和重定向规则。
- 路由页不应只是引用一个功能界面组件后结束；至少应表达这个 URL 对应的页面结构、父布局关系或路由状态边界。
- 路由页也不应塞入大量业务逻辑、复杂表格/表单实现、重复 UI 单元、深层交互细节或大块数据处理。
- 当内容开始具有独立职责、重复结构或复杂交互时，拆到对应的 `src/features` 业务目录；领域中立的基础小组件可放到 `src/components`。不得在 `src/views` 下创建页面同名组件目录。
- `src/features` 中的父组件需要继续拆分时，使用父组件文件与父组件同名目录并列的结构；`src/components` 确需多级拆分时也遵循该规则。

## 路由守卫与鉴权

- 页面级访问控制优先靠近路由页：例如 `definePage` route meta、页面级 `beforeEnter`、进入前数据存在性检查、权限不足重定向、feature flag 拦截。
- 父布局路由可以承载该路由分支共享的访问规则；子页面只补充自己的差异规则。
- 涉及登录态时，优先用父级布局路由表达认证区和登录后业务区，并在登录后业务区父路由承载共享鉴权。
- 全局登录态恢复、token 刷新、基础认证初始化、租户上下文初始化、埋点基础设施等横切逻辑，放在路由初始化、全局守卫、app 级 store 或 provider 等已有接入边界。
- 权限、租户、feature flag 等具体业务语义留在 app 层解释；`@ngt/ui` 不读取 app 路由名、权限表或租户配置。
- 不要为了复用把具体业务权限规则写进公共包；公共包最多提供通用菜单、面包屑、图标、主题等机制。

当前模板结构：

```txt
src/views/
  index.vue
  home.vue
  home/
    welcome.vue
    about.vue
```

- `index.vue` 将 `/` 重定向到 `/home`。
- `home.vue` 是 `/home/*` 的轻量父布局，并重定向到 `/home/welcome`。
- `home/welcome.vue` 和 `home/about.vue` 是仅用于证明路由、主题与 i18n 可用的最小页面。

业务 app 需要认证区时，可以扩展为以下结构；这不是当前模板已有页面：

```txt
src/views/
  auth.vue
  auth/
    login.vue
  home.vue
  home/
    feature1.vue
```

- `auth.vue` 可以作为 `/auth/*` 的认证区布局壳，承载登录、注册、找回密码等认证页共享布局。
- `auth/login.vue` 可以作为登录页。
- 业务 app 的 `home.vue` 可以作为 `/home/*` 的登录后业务区布局壳，优先承载该业务区共享的登录鉴权、权限 meta、进入条件和重定向规则。
- `home/*` 子页面只补充自己的差异权限、feature flag 或业务进入条件，不重复写基础登录鉴权。
- 不要为了登录鉴权额外发明与路由结构无关的目录；优先让访问规则跟随对应父路由。

## 路由结构设计

- 新增功能或页面前，先设计路由结构，再写页面实现。
- 不要害怕使用多级路由；业务位置、导航层级和内容区结构天然分层时，应使用多级路由表达。
- 涉及主内容区替换、详情区切换、子功能切换、工作台不同内容视图的功能，优先考虑通过路由实现。
- 根据截图、设计稿或需求识别导航菜单时，同一级菜单项默认都代表同级路由；如果暂时只有某个页面有细节要求，也应为同级菜单补齐空白占位路由，除非开发者明确说明某项只是按钮、分组或外链。
- 为菜单项补齐占位路由时，保留正确的父布局、URL 层级、route meta、i18n 文案和导航顺序；页面内容可以是最小空白占位，不要把多个同级菜单塞进当前页面状态。
- 只有明显不符合路由定义的局部状态，才留在组件状态或普通条件渲染中。
- 多级路由应让 URL 表达当前业务位置，并支持刷新恢复、浏览器前进后退和直接访问。
- 路由层级应服务业务语义和内容组织，不为了减少文件数量把多个可独立定位的内容区塞进一个页面组件。
- 如果不确定内容区替换应走路由还是组件状态，先说明两种方案的 URL 语义和交互影响，并询问用户确认。

## Route Meta

路由 meta 可以承载通用导航信息：

- `titleKey`：可翻译的页面标题或导航标题 key；菜单、面包屑和浏览器文档标题会在渲染时解析，并随 locale 更新。
- `title`：不需要翻译的静态页面标题或导航标题；仅在没有 `titleKey` 时使用。
- `icon`：菜单图标。
- `order`：菜单排序。
- `group`：由路由分组目录自动生成，例如 `(management)` / `(documents)`。
- `type`：菜单分组或过滤类型。
- `auth` / `permission` / `feature`：页面级访问控制语义，由 app 层守卫解释。

这些 meta 会被 `@ngt/ui` 的路由菜单和面包屑能力使用。

需要国际化的标题必须保存稳定的 `titleKey`，不要在 `definePage` 初始化阶段把 `$i18n.t(...)` 的结果写入 `title`，否则 locale 变化后标题仍会停留在初始语言。

## 规则

- 新增页面时同步考虑路由标题、导航展示和 i18n 文案。
- 新增页面前，先判断它是否真的需要独立 URL。
- 新增功能或页面前，先设计可能需要的路由层级和 URL 状态。
- 还原导航菜单时，必须识别菜单项对应的路由集合；同级菜单除非明确不是页面，否则应同步建立同级路由或占位路由。
- 影响分享、刷新恢复、浏览器前进后退的轻量状态，优先考虑放进 URL。
- 涉及内容区替换的功能，优先考虑路由化，除非明显不符合路由定义。
- 只影响当前页面临时交互的状态，留在组件状态。
- 业务权限、租户、feature flag 等过滤逻辑留在 app 层；页面级访问规则靠近路由页，全局横切逻辑放在路由初始化、全局守卫、app 级 store 或 provider 等已有接入边界。
- 不把具体路由假设写进 `@ngt/ui`。
- 路由类型和自动生成文件由工具维护，不手改 `types/auto`。

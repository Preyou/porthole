# Module Anatomy

app 目录围绕页面、业务能力和应用基础设施组织。

## 工程优先

实现功能前，先判断它在现有工程系统中的位置，而不是直接把代码插入当前文件。

必须先确认：

- 它属于哪个路由位置、父布局、业务模块或 feature。
- 它是否复用已有布局、组件、状态、数据模型或交互语义。
- 它是否引入新的可复用结构，或会让相邻页面出现重复代码。
- 它应复用当前业务组件、`@ngt/ui`，还是在当前 feature 内封装。
- 它是局部 UI 状态，还是应当由 URL 表达。

默认优先维护路由、模块、组件、状态和数据流的一致性；新增代码应融入已有 feature，而不是绕开现有结构新建孤岛。

## 放置规则

- 页面放在 `src/views`，由自动路由插件生成路由。`src/views` 只能包含真实路由页面，每个文件都必须直接对应一个 URL 页面或父布局路由。
- 禁止在 `src/views` 放非路由组件、composable、状态、工具、测试或其他页面辅助文件；文件路由插件会把其中的 `.vue` 文件当作路由处理。
- 路由页允许直接承载页面布局、父子路由编排、URL 状态桥接和少量轻量业务；不要为了“页面必须为空壳”而机械转发到单个 feature 组件。
- `src/components` 放重复使用的小组件，通常不带具体业务功能。
- `src/components` 内按功能分组，例如：

```txt
src/components/
  card/
    TotalCard.vue
    MessageCard.vue
```

- `src/components` 通常保持较浅。基础组件确需拆分子组件时，父组件文件与父组件同名目录并列，子组件放入该目录。

- `src/features` 放已经实现一定功能边界的组件。该组件不一定会被复用；只要出于拆分、独立性、可读性或复杂度控制值得单独封装，就可以放到 feature。
- `src/features` 内按业务父子关系组织文件，结构必须反映真实组合层级。例如：

```txt
src/features/
  User.vue
  user/
    UserInfo.vue
    UserBuild.vue
```

- `src/app` 只在需要全应用级接入点时使用，例如 `AppProviders.vue`、全应用 provider/context、启动初始化编排。不要把 feature、页面私有 provider 或普通共享组件放进 `src/app`。
- 只服务单个页面的组件、工具、状态和 provider 放在对应的 `src/features` 业务目录；简单且无需拆文件的逻辑可以直接留在路由页，但不得在 `src/views` 新建辅助目录或文件。
- 跨页面复用但仍有业务语义的能力，放在 app 内共享位置。
- 领域中立且跨 app 可复用的能力，再考虑上提到 `@ngt/ui`。

## 组件层级

- 写组件前，先设计组件层级，不把多个稳定结构和多段独立职责堆进一个组件。
- 当组件开始同时承载多个相对固定、功能单一的结构时，应勇敢拆分子组件。
- 路由页可以负责少量页面布局、父子路由编排、URL 状态桥接和业务流程入口，不要只引用一个功能界面组件后结束。
- 路由页不应长期承载复杂表格/表单实现、大量业务逻辑、多个重复 UI 单元的完整 markup 或深层交互细节。
- 当前页面、相邻页面或同批设计稿状态中，同一结构骨架出现 2 次以上时，应优先抽出组件，再用数据和 `v-for` 驱动差异内容。
- 子组件应表达稳定的结构、清晰的职责或可读的组合边界，而不是为了拆分而拆分。
- `src/features` 的组件组合层级应反映在文件结构中：父组件文件与承载子组件的业务目录并列，直接子组件放入该业务目录，复杂子组件再拥有自己的子目录。
- `src/components` 如果确需形成多级组件结构，也遵循相同的父组件文件与同名目录规则；不要把该规则应用到 `src/views`。
- 如果 `A` 由 `B`、`C` 组合，且 `C` 又由 `D`、`E` 组合，推荐结构为：

```txt
src/features/
  A.vue
  a/
    B.vue
    C.vue
    c/
      D.vue
      E.vue
```

- 子组件只被父组件使用时，优先放在父组件对应的 feature 业务目录内，不上提到全局共享目录。
- 子组件开始跨页面或跨 feature 复用且不带具体业务功能时，再考虑移动到 `src/components`、`@ngt/ui`。
- 重复结构的放置层级按复用范围决定：
  - 只在当前页面复用且带业务语义：放到 `src/features` 下对应页面或业务 feature 的目录。
  - 在同一 feature、同一路由分组或相邻页面复用：放到 feature 或 app 内共享目录。
  - 跨 app 且领域中立：说明影响范围和公开契约变化，获得授权后再考虑上提到 `@ngt/ui`。
- 拆分后保持数据流清晰，父组件负责业务编排，子组件负责局部结构和交互。

## 修改原则

- 修改前先阅读相邻页面、feature 和现有 app 约定。
- 新增功能、组件、页面时，优先参考临近页面和临近功能，保持目录组织、命名、交互和视觉风格一致。
- 新增页面或功能时，同步考虑路由层级和组件层级，不用单文件硬塞完整功能。
- 局部功能也要检查父路由、同级页面和相邻组件，确认当前实现属于已有结构还是需要新增子路由、对应页面 feature 中的组件或 app 共享组件。
- 不为了单个页面需求扩大全局结构。
- 不直接引用公共包内部路径。
- 不要手改自动生成目录。
